# P2：登录与权限、流式对话、实时通知

## 要解决的问题

P1 做完之后，系统里"你是谁"全靠请求参数：`/chat` 里的 `user_id`、工单操作里的 `operator` 都由调用方自己填，谁都能冒充别人。另外，界面上客户要干等 4～5 秒才看到回复，坐席不刷新页面就不知道来了新工单。

## 做了什么

**1. 账号与角色**（`V3__auth_and_trace.sql`、`auth/`）

| 角色 | 能做什么 |
|---|---|
| 客户 | 和客服对话、看自己的会话；可以自己注册 |
| 坐席 | 处理工单、查看任何客户的对话记录（带处理过程）、检索知识库 |
| 管理员 | 坐席的全部 + 维护知识库、运行状态、账号管理（创建坐席、停用账号） |

启动时自动创建演示账号，密码都是 `demo123`：`u1001` / `u1002`（客户）、`agent-01` / `agent-02`（坐席）、`admin`（管理员）。用户名和 P1 测试数据里的 user_id、坐席 ID 一致，登录后能直接看到以前的会话和工单。

**2. 登录与令牌**

```
登录 ──▶ 访问令牌（JWT，15 分钟，每个请求带上，服务端只验签不查库）
     └─▶ 刷新令牌（随机串，7 天，Redis 只存它的 SHA-256；每用一次作废换新）

请求 ──▶ 验签 + 过期 + 签发者 ──▶ Redis 吊销名单（登出的 jti、停用账号的"某时刻之前全部作废"）──▶ 按路径的角色规则 ──▶ 业务代码里的数据范围
```

- 身份一律从令牌里取：`/chat` 里的 `user_id`、工单操作里的 `operator` 即使传了也被忽略。
- 连续输错 5 次密码锁定 15 分钟（Redis 计数）。用户名不存在时也做一次 BCrypt 比对，防止通过响应时间判断账号是否存在。

**3. 流式对话**（`POST /chat/stream`，SSE）

每个处理环节开始和结束时各推一条事件。客户看到的是"理解你的问题 ✓ → 查找相关资料 ✓ → 组织回答…"，而不是对着空白干等。回复本身在校验通过之后整段推送。

**4. 实时通知**（`GET /notifications/stream`，SSE）

- 建单、认领、解决等工单变化在**事务提交之后**发到 Redis Pub/Sub。
- 每个实例收到后，推给连在自己身上的浏览器：坐席收到全部变化，客户只收到自己工单的变化。
- 客户的对话里会出现"坐席小周 已接手你的问题"；坐席不刷新页面就能看到新工单弹窗，导航上的待分配数量也会实时更新。

**5. 处理轨迹落库**

每条客服回复的意图置信度、路由、各环节耗时、降级环节和校验结果，以 JSON 存在 `chat_message.trace` 里。坐席查看任何一条历史回复，都能看到"处理过程"图，不只是刚刚发出的那一条。

前端端到端测试（Playwright，对接按真实接口格式写的模拟后端，三个浏览器窗口：客户、agent-01、agent-02）：

- 客户发消息后，各环节进度逐条出现。
- 坐席在不刷新页面的情况下收到新工单提醒，认领后客户那边实时显示"坐席小周 已接手"。
- agent-02 打开同一张工单，不能解决别人处理中的工单。
- 访问令牌过期后，几个并发请求只触发一次刷新，用户无感知。
- 刷新页面后登录状态保持；退出后刷新仍是登录页。
- 管理员停用的账号无法登录。
- 手机宽度下页面没有横向溢出。

## 设计决定（面试会问）

**1. 为什么用 JWT，不用 Session？**
Session 要么存在单个实例的内存里（多实例时要做粘性会话），要么集中存到 Redis（每个请求查一次）。JWT 把身份和角色签在令牌里，服务端只验签名，任何实例都能处理，而且 SSE 长连接重连到哪个实例都一样。
JWT 的代价是"签出去就收不回来"，所以加了两样东西：访问令牌只给 15 分钟，再配一份 Redis 吊销名单（见第 3 条）。这样每个请求要多查两次 Redis，但比查数据库轻得多，而且换来了"随时能让令牌失效"。

**2. 为什么要分访问令牌和刷新令牌？**
访问令牌每个请求都带着，暴露面最大，所以有效期要短；但有效期太短，用户就得频繁重新登录。刷新令牌只在换新令牌时才发出去，暴露机会少，可以给得长一些。两者分开，同时兼顾了安全和体验。

**3. 刷新令牌为什么只存哈希？为什么每次都换新的？**
- **只存 SHA-256**：Redis 数据即使泄露，拿到的也只是哈希，无法反推出能用的令牌，和密码只存哈希是一个道理。
- **轮换**：每用一次就作废，同时发一个新的。如果刷新令牌被盗，攻击者和正主谁先用，另一个就会失效，被盗的令牌最多只能用一次。
- **并发安全**：作废用的是 Redis `GETDEL`，"读出并删除"是一步原子操作。测试里 10 个请求同时拿同一个刷新令牌，只有 1 个成功。如果写成先 GET 再 DEL，会有好几个请求同时读到、同时成功。
- **前端配合**：前端也做了配合，同一时刻只发一个刷新请求，其他请求等它的结果。否则页面上几个接口同时发现令牌过期、同时去刷新，只有一个能成功，剩下的会把用户踢下线。

**4. 登出和停用账号怎么让 JWT 立即失效？**
- **登出**：把这个令牌的 `jti` 写进 Redis 黑名单，过期时间设成令牌本身的剩余有效期，到期自动清理，名单不会无限增长。
- **停用账号**：写一条"这个时间点之前签发的令牌全部作废"，同时删掉这个用户的所有刷新令牌。
- **一个细节**：JWT 的签发时间只精确到秒，所以比较用 `<=`，和停用发生在同一秒签发的令牌也会作废。重新启用账号时，不清除这个标记，否则停用前签发、还没过期的旧令牌会重新生效；这个标记 15 分钟后自动过期。

**5. 权限规则放在哪里？**
分两层：
- **路径级**（`SecurityConfig`）："只有客户能发消息""工单只有坐席能看"。这类规则在进入控制器之前就拦下了。
- **数据级**（业务代码）："客户只能看自己的会话"。这类规则和数据有关，路径上体现不出来。

客户如果传了别人的会话 ID，返回 404 而不是 403，和"会话不存在"无法区分，避免被用来探测别人的会话是否存在。

**6. 为什么用 SSE，不用 WebSocket？**
这里只需要服务端单向推送：环节进度、工单通知。SSE 就是一个普通的 HTTP 响应，有三个好处：
- 可以直接用 Spring Security 的 Bearer 令牌鉴权；
- 经过代理、网关不需要额外配置；
- 断线后重连很简单。

WebSocket 是双向的，适合聊天室那种双方都频繁发消息的场景；在这里，客户发消息本来就是一次普通的 POST。

**7. 前端为什么用 fetch 读 SSE，不用浏览器自带的 EventSource？**
EventSource 不能设置请求头，没法带 `Authorization: Bearer`，只能把令牌放进 URL，而 URL 会出现在服务器访问日志、代理日志和浏览器历史里。用 fetch 读取流式响应，可以带请求头，还能发 POST。

**8. 流式对话为什么不逐字输出回答？**
客服回答在发出前要经过校验（是否有依据、是否需要转人工）。如果逐字推送，客户会先看到还没校验过的内容，校验不通过时已经撤不回来了。所以流式推的是处理进度，回答在校验通过后整段发出。
如果以后要逐字输出，可以先生成、再快速校验、最后"模拟打字"往外推，但那只是交互效果，体验上的意义大于实际。

**9. 工单通知为什么要在事务提交之后发？为什么要经过 Redis？**
- **为什么在提交之后**：如果在事务里发通知，坐席收到"新工单 #12"点进去，可能事务还没提交（查不到），甚至事务最终回滚了（工单根本不存在）。这里的做法是业务方法返回（此时事务已经提交）之后，再调用通知。
- **为什么经过 Redis**：浏览器的 SSE 连接可能连在任何一个实例上，所以先通过 Redis Pub/Sub 广播，每个实例再推给连在自己身上的浏览器。
- **代价**：Pub/Sub 不持久化，坐席那一刻不在线就收不到。但这只是提醒，工单本身在数据库里，打开工单页就能看到。如果要求"不漏通知"，应该换成消息队列，或者用 Redis Stream 加消费组。

**10. SSE 和 Spring Security 一起用要注意什么？**
SSE 响应结束时，Servlet 容器会再做一次 ASYNC 分发。默认情况下 Spring Security 会对这次分发重新鉴权，但无状态配置下这时已经没有 SecurityContext，就会报 "Unable to handle the Spring Security Exception because the response is already committed"。解决办法是对 `DispatcherType.ASYNC` 直接放行：请求开始时已经鉴权过了。

**11. 刷新令牌为什么放在 localStorage？**
这是一个取舍。localStorage 能被页面上的脚本读到，站点一旦有 XSS 漏洞，刷新令牌就会泄露。更稳妥的做法是放进 `HttpOnly + SameSite=Strict` 的 Cookie，脚本读不到；但改用 Cookie 之后就要处理 CSRF。
这个项目是本地演示，选了更简单的方案，用后端的"单次使用 + 可吊销"把风险降下来。访问令牌只放在内存里，不落盘。

## 已知局限

- 注册没有验证码和邮箱或手机验证，演示用。
- 没有"修改密码"和"找回密码"。
- 工单通知不持久化，离线期间的通知会丢，但工单数据不会丢。
- 流式对话推的是环节进度，不是逐字输出（原因见第 8 条）。

## 简历上这一步可以写什么
