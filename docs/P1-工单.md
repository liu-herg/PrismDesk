# P1 第四步：转人工工单

## 要解决的问题

系统已经能判断"这个问题需要人工"（`escalated=true`），但判断完就结束了：没有人接手，也查不到后续。

## 做了什么

**1. 转人工自动建单**
`/chat` 判断需要转人工时自动建单，响应里返回 `ticket_id`。建单原因会记录具体是哪个信号触发的：用户要求人工 / 紧急程度 CRITICAL / 回答校验建议 / Agent 回答建议。

**2. 状态机**（`TicketAction`）

| 操作 | 允许的当前状态 | 目标状态 | 谁能做 |
|---|---|---|---|
| claim 认领 | 待分配 | 处理中 | 任何坐席 |
| release 退回 | 处理中 | 待分配 | 仅当前处理人 |
| resolve 解决 | 处理中 | 已解决 | 仅当前处理人 |
| close 关闭 | 待分配、已解决 | 已关闭（终态） | 任何坐席 |
| reopen 重新打开 | 已解决 | 处理中（交还原处理人） | 任何坐席 |

非法转移返回 409，非处理人执行 release / resolve 返回 403。

**3. 接口**

```
GET  /tickets?status=pending&assignee=&before_id=&size=20   列表（游标分页）
GET  /tickets/{id}                                          详情 + 操作记录
POST /tickets/{id}/{claim|release|resolve|close|reopen}     body: {"operator":"agent-01","version":0,"note":"..."}
```

**4. 表**：`ticket`、`ticket_event`（`V2__ticket.sql`）

## 实测

`TicketConcurrencyTest`（真实 MySQL，10 个坐席同时操作同一张工单）：

| 场景 | 结果 |
|---|---|
| 先查后改（不加锁） | **10 个都以为自己认领成功**，工单实际只属于最后写入的 agent-9 |
| 乐观锁 | 成功 1 个，冲突 9 个（返回 409），认领记录 1 条 |
| 同一会话 10 个请求同时转人工 | 新建 1 张，其余 9 个请求拿到的是同一张 |

接口手动验证（2026-11-11）：转人工自动建单 → agent-01 认领成功（版本 0→1）→ agent-02 再认领返回 409 → agent-02 去解决返回 403 → agent-01 解决成功（版本 1→2）→ 操作记录 create / claim / resolve 三条。

## 设计决定（面试会问）

**1. 抢单为什么用乐观锁，不用悲观锁（`SELECT ... FOR UPDATE`）？**
抢单的特点是冲突集中在很短的时间内，并且**输的一方不需要等**——工单被别人抢走了，等锁释放后也没用，直接告诉他"已被认领"就行。乐观锁正好是这个语义：不加锁，提交时检查，冲突就失败。悲观锁会让 9 个坐席排队等第 1 个提交，然后再一个个发现"状态已经不是待分配了"，白等一趟，还占着数据库连接。
反过来，如果是"冲突频繁、并且失败重试代价很高"的场景（比如扣库存要保证最终扣成功），悲观锁或者数据库原子更新更合适。

**2. 乐观锁具体怎么实现的？**
`UPDATE ticket SET ..., version = version + 1 WHERE id = ? AND version = ?`，影响行数为 0 就说明读和写之间有人改过，本次作废、返回 409。没有用 MyBatis-Plus 的 `@Version` 插件，而是把条件直接写在 SQL 里，原理一目了然。

**3. 只判断状态（`WHERE status = 'PENDING'`）不就够了，为什么还要版本号？**
对"认领"来说，只判断状态确实够了。但版本号还能防另一类问题：**基于过期页面的操作**。比如坐席 A 打开工单页面后去倒了杯水，这期间工单被退回、又被 B 认领、B 又退回了，状态还是"待分配"，但内容和历史都变了。A 回来点"认领"时带上页面上的版本号，就能发现"你看到的已经不是最新的了"。所以接口支持可选的 `version` 参数。

**4. "先查后改"具体会出什么问题？**
10 个坐席同时读到"待分配"，都通过了 Java 里的 `if (status == PENDING)` 判断，然后都执行了 `UPDATE ... WHERE id = ?`。每个人都收到"认领成功"，但工单最终只属于最后写入的那个人——其他 9 个人以为自己在处理，实际上没有。测试里用 `CyclicBarrier` 让所有线程"都读完再一起写"，把这个最坏情况固定下来，保证每次都能稳定复现。

**5. 同一会话为什么不会重复建单？**
不是先查"有没有未结工单"再决定建不建——两个并发请求可能都查到"没有"。而是直接插入，靠数据库唯一约束兜底，冲突了再把已有的那张查出来返回。
MySQL 没有"部分唯一索引"（PostgreSQL 有 `WHERE status IN (...)`），用**生成列**实现：`open_conversation_id` 在未结时等于会话 ID、已结时为 NULL，再给它建唯一索引。唯一索引允许多个 NULL，所以已关闭的历史工单不受限制。

**6. 为什么状态更新和操作记录要放在一个事务里？**
如果状态改了但记录没写进去，就查不到"是谁、什么时候改的"；如果记录写了但状态更新失败（比如乐观锁冲突），就会出现一条"认领成功"的假记录。测试里专门断言了：10 个坐席抢单，操作记录里只有 1 条 CLAIM。

**7. 建单失败会影响用户收到回复吗？**
不会。回复已经生成了，建单失败只记错误日志，响应里 `ticket_id` 为空。这和对话落库的处理方式一致。代价是可能漏建单，后续可以改成 MQ 异步建单 + 重试来保证可靠性。

## 已知局限

- 坐席身份由调用方传 `operator`，还没接入登录鉴权；接入后改为从登录态里取。
- 转人工的判断规则比较粗：Agent 的回答里只要出现"转人工"等字样就算。这是产品策略问题，不是工单系统本身的问题；建单原因里记录了触发信号，方便后续统计和调整。
- 已解决的工单不算"未结"，同一会话再次转人工会新建一张，而不是重新打开旧的。

## 简历上这一步可以写什么

> 设计转人工工单模块：状态机约束工单流转（非法转移拒绝），坐席抢单基于版本号乐观锁实现，并发测试中 10 个坐席同时认领仅 1 个成功（"先查后改"写法下 10 个都认为自己认领成功）；用 MySQL 生成列 + 唯一索引实现"每个会话仅一张未结工单"，转人工建单幂等；状态变更与操作记录同事务提交。
