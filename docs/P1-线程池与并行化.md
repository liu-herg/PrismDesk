# P1 第三步：线程池、并行化、超时降级

## 现状：一轮对话串行调用 5 次 LLM

| 顺序 | 环节 | LLM 调用 | 依赖 |
|---|---|---|---|
| 1 | memory：读记忆 | 无（Redis + MySQL） | — |
| 2 | intent：意图识别 | 1 次 | 最近几轮对话 |
| 3 | knowledge：知识库检索 | 2 次（改写问题、结果重排） | 只依赖用户问题；意图只决定"查不查" |
| 4 | generate：Agent 生成回答 | 1 次 | 意图、知识、记忆 |
| 5 | verify：回答校验 | 1 次 | 回答 |
| 6 | persist：写记忆、落库 | 无 | 回答 |

原代码还有两个问题：
- 多 Agent 并行、子查询并行用的是 `CompletableFuture.supplyAsync()` 的默认线程池 `ForkJoinPool.commonPool()`；
- 多 Agent 的 `join()` 没有超时，一个 Agent 卡住，整个请求就一直挂着。

## 做了什么

**1. 耗时统计**
`StageTimer` 记录每个环节的耗时，三处可见：接口响应里的 `total_ms` / `stage_timings_ms` / `degraded_stages`；每个请求一行日志；Micrometer 指标 `prismdesk.chat.stage{stage=...}` 和 `prismdesk.chat.total`（可在 Prometheus 里看 P95）。

**2. 两个自定义线程池**（`ExecutorConfig`）

| 线程池 | 跑什么 | core / max / 队列 |
|---|---|---|
| `stageExecutor` | 顶层环节：意图识别、知识库检索 | 16 / 32 / 32 |
| `workerExecutor` | 叶子任务：子查询、多 Agent 执行、回答校验、画像更新 | 16 / 48 / 64 |

**3. 意图识别和知识库检索并行**
两者互不依赖。检索是"投机"执行的：先用不调 LLM 的规则预判（`recognizeOffline`，毫秒级），只有预判明确不需要知识库（如打招呼）时才不提前检索。

**4. 超时和降级**

| 环节 | 超时 | 降级方式 |
|---|---|---|
| intent | 5s | 用规则预判的结果，仍能路由到正确的 Agent |
| knowledge | 8s | 不改写、不重排，直接检索（纯内存，毫秒级） |
| verify | 5s | 按"通过"处理，不拖住已生成的回答 |
| 多 Agent 中的单个 Agent | 30s | 该 Agent 记为失败，其他 Agent 的结果照常返回 |

用 `echomind.pipeline.parallel`（环境变量 `PIPELINE_PARALLEL`）可以切回串行，方便对比。

## 实测对比

```powershell
# 串行
$env:PIPELINE_PARALLEL = "false"; docker compose up -d prismdesk
.\scripts\bench.ps1 -Label serial
# 并行
$env:PIPELINE_PARALLEL = "true"; docker compose up -d prismdesk
.\scripts\bench.ps1 -Label parallel
```

8 个不同的问题，各发一次（另有 1 次预热不计入），单位 ms：

2026-11-11 实测，DeepSeek 模型：

| 模式 | total 平均 | total 中位数 | total 最大 | memory | intent | knowledge | generate | verify | persist |
|---|---|---|---|---|---|---|---|---|---|
| 串行 | 5160 | 4878 | 6668 | 2 | 839 | 1571 | 1542 | 1004 | 200 |
| 并行 | 4361 | 4014 | 5290 | 2 | 922 | 1636 | 1370 | 1074 | 275 |
| 变化 | **-15.5%** | **-17.7%** | **-20.7%** | | | | | | |

**怎么读这组数据：**
- 串行时各环节之和 5158 ms ≈ 总耗时 5160 ms，说明完全是一个接一个执行的。
- 并行时各环节之和 5279 ms，但总耗时只有 4361 ms，差值约 920 ms ≈ intent 的耗时：意图识别被完全"藏"在了知识库检索后面，从"两者相加"变成了"取两者较大值"。
- 样本只有 8 个，LLM 自身响应波动较大（generate 两次相差 170 ms 就是模型侧的波动），所以对外说"降低约 15%–18%"更稳妥。

**下一步还能优化什么（按收益排序）：**
1. 回答校验改成异步（先返回回答，后台校验，发现问题再补发提示或标记工单）：约 -1000 ms。
2. 知识库检索里的"问题改写"：短问题跳过改写，或缓存高频问题的改写结果：约 -500~800 ms。
3. 流式输出：总耗时不变，但用户等待第一个字的时间从 4 秒降到 1 秒左右，体感提升最大。

## 设计决定（面试会问）

**1. 为什么不用默认的 `ForkJoinPool.commonPool()`？**
它的线程数是 CPU 核数 - 1，为 CPU 密集型任务设计。这里的任务是调 LLM 的阻塞 IO，几个慢请求就能把它占满；而且它是整个 JVM 共享的，并行流、其他库的异步任务都会受影响，出了问题很难定位。自定义线程池可以独立设置大小、命名线程（日志和线程 dump 里一眼能认出来）、单独监控。

**2. 线程池参数怎么定的？**
- 任务几乎全是等网络返回，不按"CPU 核数 + 1"那套公式；按**要支持的并发对话数**估：每轮对话在 stage 池最多占 2 个线程，core=16 约支持 8 轮同时处理，突发时扩到 max=32。真正的上限其实是下游 LLM 的限流。
- **队列故意不大**。`ThreadPoolExecutor` 的规则是：先用 core 线程 → core 满了进队列 → **队列满了才创建超过 core 的线程** → 到 max 还不够才拒绝。队列设成几千，max 就永远不会生效，任务只会排队变慢。
- 拒绝策略用 `CallerRunsPolicy`：池和队列都满时，由提交任务的线程（Tomcat 请求线程）自己执行。效果是自动退化成串行——请求变慢但不丢、不报错，同时请求线程被占住，对上游形成反压。
- 这些数字是起点，不是结论：上线后看 Micrometer 的线程池指标（活跃线程数、队列长度）再调。

**3. 为什么要两个线程池？**
知识库检索这个"父任务"内部会并行提交多个子查询并等待它们。如果父子任务共用一个池：池满时，父任务占着所有线程等子任务，子任务在队列里等线程——互相等待，这叫**线程饥饿死锁**，而且不会报任何错，只是所有请求都超时。按任务层级分成两个池后，父任务等待的子任务永远在另一个池里执行。

**4. "投机执行"会不会浪费 LLM 调用？**
会，所以加了规则预判：只有预判说"明显不需要知识库"时才不投机。实际浪费只发生在"规则判断需要、LLM 判断不需要"的少数情况下，代价是一次改写调用，换来大多数请求省掉一个环节的等待时间。这是用成本换延迟的取舍，适合客服这种对响应时间敏感的场景。

**5. `orTimeout` 超时后，任务真的停了吗？**
没有。`CompletableFuture` 的超时只是让调用方不再等待，执行任务的线程会继续跑到下游返回为止，Java 没有安全的办法强行中止一个阻塞中的线程。所以超时必须配合两件事：下游 HTTP 客户端自己的超时（让线程最终能释放）、线程池容量（扛得住一部分线程被慢请求占着）。

**6. 降级的原则是什么？**
核心环节（生成回答）不降级，辅助环节（意图、检索、校验）各有更便宜的替代方案：规则代替 LLM、直接检索代替改写重排、跳过校验。每次降级都会出现在响应的 `degraded_stages` 和日志里，不是悄悄发生的。

**7. 为什么不用 Java 21 的虚拟线程？**
可以用，而且对这种阻塞 IO 场景很合适（Spring Boot 3.2+ 设置 `spring.threads.virtual.enabled=true`）。这里选平台线程池有两个原因：池的大小本身就是一道限流，防止瞬间向 LLM 打出过多并发；虚拟线程遇到 `synchronized` 里的阻塞会钉住载体线程（JDK 24 才修复），需要逐个排查依赖库。

**8. 加了并行后，会话锁还有效吗？**
有效。会话锁由处理请求的 Tomcat 线程持有，写记忆也在这个线程上执行（可重入）；放到线程池里的只有意图识别、检索、校验这些只读环节，它们不需要锁。

## 已知局限

- 5 次 LLM 调用里只有 2 个环节能并行，剩下的生成和校验必须串行。再往下降要靠别的手段：流式输出（让用户更早看到第一个字）、高频问题的答案缓存、把校验改成异步。
- 压测是单用户顺序请求，测的是单轮延迟，不是吞吐量。高并发下的表现要用 JMeter 之类的工具另测。

## 简历上这一步可以写什么

> 对对话链路做分环节耗时埋点（Micrometer），定位到一轮对话串行调用 5 次 LLM；将互不依赖的意图识别与知识库检索改为并行（规则预判 + 投机执行），以按任务层级隔离的自定义线程池替换默认 ForkJoinPool 公共池（避免父子任务共池导致的线程饥饿），并为各环节增加超时与降级，平均响应时间从 5.2s 降至 4.4s（约 -15%），中位数 -18%。
