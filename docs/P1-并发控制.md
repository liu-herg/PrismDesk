# P1 第二步：同一会话的并发控制

## 问题

`MemoryManager.addMessage` 的流程是：写入一条 → 查长度 → 达到 15 条就压缩。压缩分这几步：

1. 从 Redis 读出当前所有消息（快照）；
2. 调用 LLM 把较早的消息总结成摘要（真实环境要几秒）；
3. 把这些旧消息归档到 MySQL 的情景记忆；
4. **删除整个 Redis 列表**；
5. 把最近 5 条写回去。

第 1 步和第 4 步之间如果同一会话又写入了新消息，新消息不在快照里，会在第 4 步被一起删掉——**丢消息**。多个请求同时触发压缩时，同一批旧消息还会被**重复归档**。

什么时候会发生：用户连发两条消息、前端超时重试、同一账号多端同时提问。

## 复现

`MemoryConcurrencyTest`：8 个线程同时往一个会话写 320 条消息（每条内容唯一），LLM 摘要用 20ms 延迟模拟。

检查的不变量：**每条消息恰好出现一次**——要么还在工作记忆里，要么已归档到情景记忆。

同一份测试跑两遍（2026-11-11 实测；不加锁时的具体数字每次运行会有波动）：

| | 丢失 | 重复归档 |
|---|---|---|
| 不加锁 | 64 条（20%） | 218 条 |
| 加会话锁 | 0 | 0 |

运行方式（需要 docker compose 里的 Redis 在运行）：

```powershell
docker run --rm --network prismdesk_default -e IT_REDIS_HOST=redis -e IT_REDIS_PASSWORD=echomind123 -v "${PWD}:/workspace" -v prismdesk-m2:/root/.m2 -w /workspace maven:3.9.9-eclipse-temurin-21 mvn test
```

不设置 `IT_REDIS_HOST` 时这个测试会自动跳过，不影响普通的单元测试。

## 修复

引入 Redisson，按 `用户 + 会话` 加分布式锁（`lock:conv:{userId}:{convId}`），加在两处：

| 位置 | 作用 |
|---|---|
| `MemoryManager.addMessage` | 保证"写入 + 判断 + 压缩"是一个整体，修复丢失和重复 |
| `/chat` 整轮处理 | 同一会话的消息排队处理：读记忆 → 生成回复 → 写记忆。否则两条并发消息各自读到旧上下文，回复互相看不到对方 |

等待超过 15 秒（`echomind.lock.wait-ms`）拿不到锁，返回 HTTP 429"上一条消息还在处理中"。

## 设计决定（面试会问）

**1. 为什么不用 `synchronized` 或 `ReentrantLock`？**
它们只在一个 JVM 进程内有效。服务部署多个实例时，同一会话的两条消息可能落到不同实例上，本地锁管不住。

**2. 为什么不自己用 `SET key value NX EX` 实现？**
能做，但要自己处理三个问题，Redisson 都已经解决了：
- **过期时间设多久**：一轮对话要调 LLM，耗时不可预估。设短了业务没跑完锁就过期，别的请求会闯进来；设长了进程崩溃后要等很久。Redisson 的**看门狗**在持有锁期间自动续期（默认 30 秒过期、每 10 秒续一次），进程崩溃后不再续期，锁自动释放。
- **误删别人的锁**：释放时要校验"这把锁是不是我加的"，并且"校验 + 删除"必须原子（Lua 脚本）。
- **可重入**：`/chat` 持有锁期间，内部调 `addMessage` 还要再加一次同一把锁。Redisson 用 Hash 结构记录"持有者 + 重入次数"。

**3. 锁的粒度为什么是会话，不是用户或全局？**
粒度越小并发度越高。冲突只发生在同一个会话内部，不同会话之间完全不需要互斥。

**4. 持有锁期间要调 LLM，锁持有时间很长，有问题吗？**
这把锁只挡同一会话的后续消息，而同一会话本来就应该按顺序处理（否则上下文是乱的），所以长时间持有是符合业务语义的。对别的会话没有任何影响。等待设了上限，超时返回 429，不会让请求线程无限堆积。

**5. 为什么不用 Lua 脚本把压缩做成原子操作，从而不需要锁？**
压缩中间要调 LLM 做摘要、要写 MySQL，这些没法放进 Redis 的 Lua 脚本里。能原子化的只有"删除 + 写回"这一小段，解决不了"读快照之后又有新写入"的问题。

**6. Redis 挂了怎么办？**
拿锁会失败。写记忆这条路径上只记录告警，不影响本次回复（和原来 Redis 不可用时的降级行为一致）；`/chat` 入口会直接报错，因为没有 Redis 本来也读不到上下文。

**7. 这把锁有什么局限？**
- Redis 主从切换时，锁可能在新主节点上丢失（主节点还没来得及同步就宕机）。对"聊天记忆"这种场景可以接受；涉及钱的场景不能只靠 Redis 锁，要加数据库层面的唯一约束或乐观锁兜底。
- 用的是非公平锁，极端情况下等待顺序不保证先来先得。

## 简历上这一步可以写什么

> 定位并修复会话记忆压缩的并发缺陷：同一会话并发写入时，"读取快照 → LLM 摘要 → 清空重写"的非原子过程会导致消息丢失和重复归档。编写并发测试复现问题（8 线程并发写入 320 条，约 20% 丢失、超过一半被重复归档），引入 Redisson 按会话加可重入分布式锁并依靠看门狗自动续期，修复后丢失和重复均为 0。
